## 現在地と担当

同日後続の[Macローカル受入](mac-local-acceptance-20261020.md)で、架空2端末の隔離／片側停止と認証期限、期限切れ後の終了を検証・修正した。自動284件・Chrome保存操作は合格だが、実Windows／実2台の接続試験を置き換えない。修正版はクラウド未反映。次回反映時は旧CSRFセッションを閉じて新しい利用を始めるため、入力／結果の継続を案内しない。

Macは端末内の非エクスポート鍵・Cloudflare証明書・限定したChrome自動選択を設定済み。通常Chromeでホームと基本4画面、再読み込み、「利用終了」後の新規セッションが通った。先行したChrome再起動直後の403は原因未確定で、現状からの完全再起動とOS再起動後の再確認が残る。Windowsは現在操作できないため保留で、TPM読取・鍵／CSR・証明書・接続をまだ実行していない。今すぐの回答は不要。

Mac1台については、実DBのstatusだけを一時停止し既存タブの通信がDEVICE_REVOKEDで拒否されることと、元の指紋/日時/期限でDB状態を復元しChromeのホームを再表示することを確認した。復元直後の読込失敗も残り、常に無操作で戻る合格ではない。試験ではsessionsを残しており、以下の本停止時のセッション無効化・Cloudflare証明書失効・2台間の独立性は未確認。終了失敗でもローカル入力を消す修正はローカル検証済み・クラウド未配備。[実測と限界](hosted-preparation.md#windows保留中の停止復元試験とローカル修正2026-10-20)。公開環境は実AI未接続、送信停止のモックのまま。

## 初回設定

1. 管理者が対象の物理PC・普段使うOSユーザーを確認する。別の管理者ユーザーで作った鍵を移さない。Windowsでは[段階別の手順](../tools/device-cert/README.md#windows)のA（`tpm.msc`の読取）から再開する。
2. 端末内で非エクスポート鍵と公開CSRを作る。Macはlogin Keychain、WindowsはTPMのMicrosoft Platform Crypto Provider。会社の既存手段で公開CSRだけを渡す。秘密鍵ファイル・PFXは作らず、ツールからメール等を送信しない。
3. 管理者がCloudflareで証明書を発行し、端末CN・公開鍵一致・clientAuth・CA=false・期限を照合する。端末へ返すのは公開証明書だけ。Macの初回証明書は画面の最短である1年を選んだが、接続許可期限とは区別する。
4. 管理者が専用ホストのWAF指紋条件、Workerの `HOSTED_APPROVED_DEVICES`、専用DBの端末ID／指紋／有効期間をそろえる。Workerの許可リストは1〜2台だけを受け付け、未知の指紋を拒否する。アプリ用DB資格情報には端末登録や停止を行う権限を渡さない。
5. 作成時と同じOSユーザーへ公開証明書を入れ、対象ホスト・実発行者CN・端末CNに限定したChrome自動選択1件を追加する。既存ポリシーを保持する。[Mac／Windowsの操作](../tools/device-cert/README.md)
6. 対象PCでホーム・4画面・再読み込み・利用終了・新規セッション、Chrome／OS再起動後の無操作接続を確認する。管理機能、証明書なし、未登録端末、Vercel直接URLは拒否されることを別に確認する。現在のモックではAIを送信しない。

## 更新

証明書の自動更新・Chromeポリシー配布・自動失効はまだ用意していない。現在のhelperは固定CN／鍵タグを使う初回設定用で、再実行による更新には使わない。

1. 管理者が試用継続の判断と期限を確認する。現行の終了日時は **2026-10-26 08:47:54 JST**。証明書だけを更新してアプリ期限を延ばさない。
2. 継続する場合は更新用のCN・鍵タグ・CSR手順を用意し、端末内で新しい鍵を作る。これは未実装・未試験の後続作業。旧鍵をエクスポートして更新しない。
3. 有効な許可登録を最大2台に保ち、対象端末の旧登録を止めてから、WAF・Worker・専用DB・Chromeの条件を新しい指紋／証明書へ合わせる。旧新を3台目として並行許可しない。切替中は対象端末が利用できない時間がある。
4. 新しい証明書で接続・再起動・旧証明書の拒否を確認した後、旧証明書をCloudflareで失効し、対象端末の旧証明書／鍵／不要になった自動選択1件だけを片付ける。

## 端末交換

管理者が旧端末を先に[個別停止](#個別停止)する。その後、新PCで初回設定を行い、許可枠を置き換える。鍵・PFXを移送せず、旧端末の台帳・停止記録は残す。普段のWindowsユーザーを作り直す場合も、既存鍵を移して済ませる手順にはしない。2台目の独立した利用と交換の実機試験は未確認。

## 個別停止

現時点で共用アプリ内の管理ボタンや停止APIはない。会社管理者が専用環境の管理権限で操作する。既存業務DBや他プロジェクトを止める操作と混同しない。

1. 専用Supabase projectと `yamadaya_mock.devices` の対象ID・指紋を照合し、その端末だけ `status = 'revoked'` にする。復旧時に古いセッションを戻さないよう、当該端末に紐づくセッションも無効化する。費用台帳・未確定予約・他端末は変更しない。これを行う管理画面／自動化は未実装で、対象を限定した管理者SQLによる手順となる。
2. 対象PCの既存タブから次の再読み込み／API取得を試し、拒否されることを確認する。認可は各リクエストでDBの端末状態・指紋・期間を確認する。既に表示した画面や保存済みPDFを遠隔回収できるという意味ではない。
3. Cloudflareで当該証明書を失効し、WAF・Workerの許可条件からも当該指紋を外す。もう1台の許可条件は残す。失効処理の完了と対象の拒否、もう1台の継続利用を確認する。現在登録済みなのはMac1台で、2台間の独立性は後続試験。
4. 端末を操作できる場合は、対象の証明書・対応鍵と今回追加したChromeポリシーだけを削除する。他の証明書やポリシー、CAの信頼設定には触れない。

誤停止からの復旧は、元の端末・指紋・期限を照合し、新しいセッションで試す。Cloudflareで失効済みの証明書は再利用せず、端末内の新しい鍵／CSRから設定し直す。停止・復旧の実環境での結果は公開準備報告へ記録する。

## 試用終了

元の **2026-10-26 08:47:54 JST** で端末の `not_after` による接続拒否を確認する。1年の証明書が残っていても継続許可にはならない。期限終了の実時間での確認は未実施。

管理者が対象端末を停止し、Cloudflare証明書を個別失効、端末登録とセッションを無効化する。今回専用の接続秘密・DB資格情報・Storage用キーの終了処理と、画像削除を確認し、元の費用台帳・未確定予約・監査記録は保持する。Vercel／Supabaseの契約終了や既存サイトを含む全体停止を自動で行う手順にはしない。画像の定期削除schedulerの配備・通知も未完了であり、自動清掃済みとは扱わない。
